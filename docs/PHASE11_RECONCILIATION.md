# Phase 11 / Task 11-13 — 最終照合・総合検証

## 到達範囲

`GET /admin/reports/reconciliation?year=YYYY&month=M&batch_id=ID`は内部向けJSON照合API。`reports.view`・`sales.view`・`reports.reconcile`をすべて要求する。`batch_id`未指定ではARK内部の不変条件を検証する。対象が提供原本の2026-10なら`source_status=provided_without_imported_actuals`と`source_workbook_evidence`を返し、それ以外は`source_status=not_provided`。数値の実原本照合ができるまでは`source_original_verified=false`を維持する。旧Excel/Google Sheets原本の実値を読んだかのようには表示しない。

Task 11-12のstagingから登録した`historical_metric_values`を指定すると、同じ暦月・metric codeについて、旧値、ARK値、差分、比較可否、確認状態を返す。`legacy_treatment_count`は新しい来店数と定義が違うので比較不能とし、旧値は残す。未知・NULLの指標を0へ置き換えない。差異はExcelの誤りと決めつけず、`POST /admin/reports/reconciliation/{historicalMetric}/review`で権限保持者が次の分類と理由を監査付きで記録する。

- `business_definition`: 旧定義とARK定義の違い
- `source_inconsistency`: 原本内の矛盾
- `migration_gap`: 移行・取込不足
- `implementation_bug`: ARK実装の不具合
- `undetermined`: 調査中

確認状態は`confirmed`または`needs_attention`。確認しても差分値そのものは書き換えず、証跡を保持する。

## 自動不変条件

照合APIは指定月の次を機械的に検証する。`pass`、`fail`、`unknown`を分け、NULLや根拠欠損を勝手にpass/0へしない。

1. `completed` Visit件数 = 月来店数。日次各指標合計 = 月次、月次各指標 = 年間月行、年間12月合計 = 年間合計。
2. 次回予約人数 <= 来店数、初診予約 <= 初診、ロング <= 来店数、10回目 <= 6回目 <= 2回目 <= 新規。年間の予約率・到達率は分子/分母合計で検算し、月率の平均にしない。
3. 確定会計ごとにheader税抜/税/税込 = 明細合計、税込 = 受領支払内訳合計。各明細の税込 = 税抜 + 税。支払方法別合計 = 決済日基準売上。
4. 実施施術の担当時間合計 = 施術時間。欠損があれば`unknown`、既知部分の不一致は`fail`。スタッフ配分売上 = 配分対象明細売上。
5. 閉じた回数券/月額配賦契約の配賦合計 = 元契約額。有効契約の途中配賦は元契約額を超えない。
6. スタッフ月次・時間帯全体の予約可能時間基準稼働率 = 稼働分 / 予約可能分。分母0はNULL。
7. 次回予約snapshot、初診予約snapshot、離反などの未判定数は`unknown`として別表示する。

複数明細テーブルを一括JOINしない。会計、施術、配賦をそれぞれ独立した粒度で取得・検算する。返金帰属は未確定のため、返金を月売上へ自動控除しない。

### 旧資料 ↔ ARK

ARKは2026-09-27時点で対象期間（2023-04〜2026-09）の来店・入金事実を持たない（Peak Manager運用期間でARK未稼働）。したがって旧値とARK値の差額は算出せず、全件を**source missing（ARK側）**とする。以前の照合APIは事実0件の月にARK値0を返し、旧値0と「matched」、それ以外と「different」になっていた。これは**ARK bug**として修正した（`ark_source_status=no_facts`、`comparison_status=ark_source_missing`、ARK値/差額はNULL）。

外部資料待ちで残るのは次の3点だけである。

1. ARK稼働後、同一期間の実績を持つ旧帳票（またはGoogle Sheets）との数値照合。
2. 2023年新規数の2原本不一致について、どちらが正かの業務判断。
3. 旧コース名29種と6種のARKコース対応表の承認（Q13）。

## 原本入手後の比較手順

1. 旧Excel/Google Sheetsを読取専用で受領し、原本hash、対象年月、シート名/セル、基準日、売上基準、旧定義を記録する。原本を書き換えない。
2. Task 11-12の中間形式へ保護コピーから変換し、dry-run、セル出典、検証エラーを確認する。実原本の列対応は承認を受ける。顧客名だけで統合しない。
3. `historical_metric_values`へ対象集計だけを本登録し、本APIの`batch_id`を指定して各月の旧値/ARK値/差分を取得する。日次・月次・年間、支払方法・税・スタッフ・時間帯、6シートの主要セルを同じas-of dateで比較する。
4. 差異理由を5分類でレビューし、定義差/原本矛盾/移行不足/実装不具合を切り分ける。再計算・修正後も元のimport batchと監査履歴を残す。
5. Excel原本が来たら`docs/EXCEL_EXPORT.md`のテンプレートhash・レイアウト検証を実行する。既存の壊れた式はARKへ移植せず、ARK算出値を正本にする。

提供されたExcel原本は構造確認済みだが実績入力なし。**実数値照合は未実施**。自動不変条件とfixture比較はテスト対象であり、これを実原本照合と呼ばない。Google Sheets実書込、SALON BOARD連携、外部予約サイト同期、本番DB接続、未確定返金仕様の確定は行わない。
